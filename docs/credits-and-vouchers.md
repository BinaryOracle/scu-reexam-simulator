# 积分、模拟面试次数与卡密

积分与模拟面试次数是两种独立余额。普通用户默认拥有 1 次免费面试，初始积分默认 0；后台「积分与卡密」可分别配置后续新用户的初始面试次数与每次面试的积分价格，创建账号时也可指定初始次数。账号列表可单独调整剩余面试次数。管理员内部以数值 999999 表示不限次数，前台只显示“已开通”，不返回该内部额度。

签到奖励、投稿奖励、卡密兑换、周榜奖励和上机考试排名奖励全部增加积分。积分商城目前提供“模拟面试次数”商品，默认每 1 积分购买 1 次；管理员可调整每次所需积分。购买在一个 SQLite 即时事务中扣除积分并增加面试次数，重复请求使用幂等键避免重复扣款或发放。管理员免扣次数，也无需购买。已有面试次数不会迁移或复制为积分，旧次数账本仍保留原历史。

准备、选择 PPT、麦克风检测、浏览和复盘不消耗次数。PPT 转换成功并正式创建、开始面试时，在同一个 SQLite 即时事务中扣除一次；余额不足会回滚场次并清理转换文件。旧准备场次通过开始接口首次启动时扣一次，重复开始不重复扣。已有已开始的历史记录迁移后继续使用，不追扣次数。主动结束、超时和删除面试记录不返还次数，避免删除记录绕过额度限制；页面刷新后的恢复录音也不重复扣次。

`[credits].default_credits` 是数据库首次初始化的默认面试次数，默认 1；后台修改保存到 `app_settings`，不会覆盖已有用户余额。积分初始值默认为 0。`interview_points_cost` 是购买一次面试所需积分，默认 1。`max_voucher_batch` 默认 500，限制一次批量生成数量。`[credits.packages]` 仅在首次创建套餐表时导入初始套餐；运行期间 `voucher_packages` 为套餐的权威数据来源。后台新增套餐通过 `POST /api/admin/voucher-packages` 保存金额（整数分）和积分数量；同金额、同积分数量不能重复创建。删除套餐会永久删除套餐记录及该套餐下全部已发行卡密，包括未兑换卡、已兑换记录及其兑换历史；未兑换卡立即失效，已经到账的积分不回退。确认弹窗必须明确提示该不可逆影响。

卡密形如 `XXXX-XXXX-XXXX-XXXX-XXXX-XXXX`，由安全随机源从不含易混淆字符的 32 个字符中独立取 24 位，随机空间为 120 位，不包含时间戳或递增 ID。数据库为完整卡密设置唯一约束；碰撞时重试，连续失败则回滚整批，不产生重复卡密。卡密是持有者可兑换的凭证，应只向管理员及购买者提供。

后台按数据库套餐分别管理卡密，可按未兑换／已兑换、生成批次、卡密或兑换用户名查询，分页显示。生成后自动筛选本批次。导出默认筛选未兑换卡密为 TXT，一行一卡密，可由管理员手动上传联动小铺；若明确选择全部或已兑换范围，导出前会提示这些记录不能用于商品上架。本站不调用商城接口、不收款，不自动同步订单、退款或发卡。导出不会改变状态，未兑换不等于尚未售出；请按新生成批次上架，避免重复上传同一卡密。关键词搜索仅用于查看，导出按钮明确按套餐、状态与批次导出。

用户点击头像进入个人主页，可查看积分、剩余面试次数、积分流水、购买记录、卡密兑换记录及估算消费金额，并可退出登录。积分商店当前支持购买模拟面试次数。主页提供卡密输入框与兑换按钮；兑换失败会保留输入内容并给出可操作的说明。金额是已兑换卡密发行时的标价之和，不是商城实际付款凭证，无法反映外部折扣、退款或未兑换卡密。兑换接受小写、连字符或空白分组，校验后统一为标准格式。即时事务中检查卡密未使用、绑定兑换用户、增加积分并记录账本；并发兑换同一卡密仅一笔成功。普通用户只能看到自己的记录及卡密尾号，管理员才能查看完整卡密列表、生成及导出。

## 每周排行榜

每日训练和算法带刷分别展示两张榜，共四榜：每日训练打卡天数、每日训练抽题数量、算法带刷打卡天数、算法带刷通过题目数。排行榜只列启用的普通用户并显示用户名；管理员账号不参与排名。用户从对应模块打开排行榜时，只请求该模块的两张榜。排名按指标降序，用户名及账号 ID 用于稳定处理并列。

每周以北京时间周六 00:00 作为结算时刻（也就是周五结束）。四个榜单各自前三名分别获得 3、2、1 积分；没有正向记录的用户不领取奖励。结算在数据库事务中运行，服务每分钟检查一次，进程停机期间漏掉的已结束周期会在下次启动后补结算；周期、榜单名次和账本引用都有唯一约束，重复检查不会重复发放。新一周开始后榜单按新周期计算，历史奖励保留在积分账本。

SQLite v8 为后台密码查看增加密文列，v9 增加用户面试次数、场次扣减标记、`app_settings`、`vouchers` 与 `credit_ledger`。升级时已有普通用户获得当前配置的默认体验次数；重复启动不会重置余额或重新发放体验次数。删除面试不会删除兑换记录和次数账本。v10 新增 `users.is_superadmin` 与单一超级管理员索引、动态套餐表，并迁移卡密为套餐外键；v35 新增积分钱包、积分流水、积分购买和周榜结算记录。积分迁移初始为 0，不影响已有面试次数。删除用户会清理其私有数据及账本，卡密保留兑换时间与用户名快照，兑换用户 ID 可置空；使用状态及防重复兑换依据 `redeemed_at`，避免删号后已用卡密变成未用。

主要实现：`app/services/credits.py` 管理额度事务，`app/routes/credits.py` 提供个人主页、兑换及后台接口，`app/static/credits.js` 和 `credits.css` 管理对应页面。后端测试见 `tests/test_credits.py`，覆盖并发兑换、并发开始面试、迁移、金额统计、越权访问、分套餐与分批导出。

## 上机考试排名奖励

每场模拟上机考试第 1、2、3 名默认分别奖励 9、6、3 积分。在后台「卡密与积分 → 积分奖励规则 → 上机考试奖励」分别设置，允许 0 到 1000000 的整数，0 表示对应名次不发奖。配置由 `app_settings.contest_rewards` 管理，通过 `PATCH /api/admin/credit-settings` 的 `contest_rewards` 三元素数组更新；只有管理员可修改。修改前先按旧规则结算已到期且评测完成的比赛，新规则用于之后的结算；已发积分和结算快照不受修改影响。

比赛结束且比赛期间普通用户提交的代码全部进入最终评测状态后，服务每分钟检查并自动结算。打开比赛排名也会立即检查该场比赛。仍在等待桥接或评测的提交会延迟结算，完成后下次检查再发放；服务停机期间漏掉的比赛会在启动后补结算。功能首次启用前已结束的比赛不追溯发奖。关闭排名展示不影响后台结算，但前台不返回获奖人员列表。

发奖与页面排名共用 `app/services/contest_scoring.py` 的排序：分值制按总得分、通过题数、提交次数、首次通过时间、用户名排序；ACM 制按通过题数、提交次数、首次通过时间、用户名排序。只有比赛起止时间内的提交计入，部分通过按测试点比例向上取整得分。管理员不参与排名和发奖，前三名中零分者不发奖，不递补名次；不足三人时仅向实际存在的正分名次发放。

SQLite v41 新增 `contest_reward_settlements` 与 `contest_reward_grants`。每场比赛的规则快照、名次奖励与 `points_ledger` 入账在同一即时事务中提交，比赛结算主键和名次唯一约束防止并发、刷新、重启重复发奖。删除比赛保留结算快照，删除账号保留用户名快照并将获奖用户引用置空；编辑比赛不会再次发奖。两张奖励表随「积分与兑换」模块备份。当前恢复功能要求备份与程序数据库版本一致，因此升级前的 v40 备份应使用 v40 程序恢复。

比赛排名页显示当前或已结算的奖励金额，获奖用户旁显示实际到账积分；个人主页「积分明细」显示“上机考试排名奖励”。实现为 `app/services/contest_rewards.py`，由排名接口和现有 `leaderboard_scheduler.py` 调用；测试见 `tests/test_contest_rewards.py`。

## 管理员查看密码

登录继续使用 scrypt 哈希验证。为满足明确的管理员查看要求，创建／重置密码时另存 Fernet 认证加密副本，有该账号管理权限的管理员显式点击后通过专用 POST 接口解密返回，响应禁止缓存；用户列表和普通用户接口均不返回密码或密文。密码显示 15 秒后自动隐藏，也可立即点击隐藏，离开账号页或切换浏览器标签时隐藏。

普通管理员不能查看其他管理员的密码。旧账号没有加密副本时，列表明确显示“需先重置密码”，可打开密码重置对话框。旧账号的哈希不能反推原文；成功登录一次或管理员重置后建立加密副本，迁移不修改旧密码。`[security].password_key_file` 指定密钥位置，省略时使用数据库同目录的 `password-view.key`，首次创建权限为 0600。数据库和密钥必须配套备份；已有密文而密钥丢失时拒绝重新生成，错误密钥或损坏密文会明确报错，不返回假密码。

可恢复密码意味着持有数据库和解密密钥的人可以还原密码，其保护强度弱于只保存哈希的方式。密钥文件不应放进代码仓库、静态目录或卡密导出文件；本地默认 `data/` 已由 Git 忽略。

本次权限、删号、动态套餐、v9 升级与退出会话测试见 `tests/test_admin_roles_v2.py`；浏览器验证记录与截图位于 `output/playwright/admin-v3-*`，破坏性检查使用隔离数据库。

## 店铺购买入口

`credits.shop_url` 配置个人主页卡密兑换区的店铺链接，默认使用 `https://wzyp.cn/shop/E1GQFV0P`，留空可隐藏入口。仅允许 HTTP/HTTPS 链接，不能内嵌用户名和密码；该字段作为公开信息返回，不包含任何支付回调或订单对接。套餐列表仍由后台数据库维护，不在前台写死金额和次数。

## 套餐管理与邀请返利

后台「套餐管理」维护套餐名、Markdown 详情、人民币价格和返利比例（默认 5%，支持两位小数）。详情编辑器支持粘贴 PNG、JPEG、WebP 图片，图片保存到公告图片资源目录并以站内 Markdown 地址引用。它与积分卡密套餐相互独立；套餐购买登记不扣积分，也不发起支付。管理员在用户列表点击「套餐服务」汇总，选择已启用套餐登记购买。同一用户不能重复登记同一个有效套餐；误登记可移除，原始记录保留。

价格以整数分、比例以万分之一存储；每笔返利按购买价格乘以比例，四舍五入到分后汇总。购买记录保存当时的名称、价格和比例，编辑套餐只影响之后的新登记。没有邀请者的用户仍展示购买总额，返利金额为 0，状态为「未填写」。

下架套餐前会确认影响范围。下架使关联购买记录从后台与邀请页的列表、金额和返利状态计算中隐藏，不删除记录；重新启用后恢复，保留原有兑换标记。已主动移除的购买记录不会随套餐启用而恢复。

用户列表「套餐服务」显示有效购买总额和返利总额，点击查看套餐名、购买价格、返利比例及底部总返利；「返利」单列显示「未填写 / 待兑换 / 已兑换」。管理员每次切换状态前需确认，操作作用于当前有效购买记录。新增购买保持旧记录的兑换标记，新记录处于待兑换状态；明细同时显示待兑换与已兑换金额，确认弹窗列出两者，避免将总返利误认为本次待兑换金额。当前有效记录中只要存在未兑换记录，汇总状态即为待兑换。下架记录的兑换标记不受切换影响。

邀请返利页与后台共用购买明细展示；邀请者只能查询其邀请用户的记录。普通管理员只能管理普通用户的购买与返利。旧的手填购买说明保留为仅后台可见的历史备注，不推测金额、套餐或兑换状态；管理员可根据实际购买情况重新登记。原手填写入接口已移除。

数据库版本为 42，新增 `service_packages` 和 `service_package_purchases`；备份归入「积分与兑换」，随账号一并导出与恢复。升级后需重启后端加载新接口并执行数据库迁移。
